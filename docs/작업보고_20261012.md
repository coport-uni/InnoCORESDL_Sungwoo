## 1. 문제 진단

### 증상

`demo_cell5_fan_blink.yaml`의 dry-run(`python -m orchestrator validate`)이 다섯 개 fan 스텝 모두에서 `unknown_action fan/state`, `fan/switch`로 실패했습니다. 그런데 cell5(`192.168.0.120:17062`)의 `/v1/health`는 정상이었고 OpenAPI에는 `hotplate/*`, `lamp/*`까지 있었지만 `fan/*`만 없었습니다.

### 원인

| # | 사실 | 확인 방법 |
|---|---|---|
| 1 | 선풍기 액션 세트(#39)는 **이 체크아웃의 작업 트리에만** 있고 HEAD(`57de7af`)에는 없음 | `git show HEAD:server/routes.py`에 `fan` 0건 |
| 2 | 포트 17062의 프로세스는 NUC2의 **다른 체크아웃** `InnoCORESDL_shinyeong`(`f72da9d`, #29 머지 시점)에서 뜬 것 | `pgrep`은 상대 경로만 보여 줌; `readlink /proc/439795/cwd`로 확인 |
| 3 | 그 런처 `claude_test/test_cell5_server_shinyeong.py`는 스마트 플러그를 아예 열지 않음(`plug=None`) | 소스 확인. 선풍기 코드가 있었어도 `/v1/fan/*`는 409였을 것 |
| 4 | 런처의 존재 이유였던 "핫플레이트 없음"은 더 이상 사실이 아님 | NUC2 `find_rct_port()` → `/dev/ttyACM0`, 드라이버가 `RCT digital` 읽음 |

### 배포 대상 선택

작업자가 `server/secure.env`에 적어 준 NUC2 디렉토리는 `InnoCORESDL_Sungwoo`였고, 그 체크아웃은 NUC1과 같은 HEAD(`57de7af`)에 `.venv`(kasa 0.10.2, sy01b, mks_motor, fastapi 모두 import 가능)와 서브모듈이 갖춰져 있었습니다. `_shinyeong` 체크아웃은 오래된 커밋이라 215줄짜리 cell 변경을 덧씌우기엔 위험했으므로, `_Sungwoo`를 배포 대상으로 썼습니다.

## 2. 변경 내용

### 2.1 cell5 테스트 런처 — 스마트 플러그 개방

`claude_test/test_cell5_server_shinyeong.py` (미커밋 파일, 이번 세션에 수정)

- `_load()`가 `[lamp]`/`[fan]` 테이블을 읽어 `lamp_target`(기본 `"all"`)과 `fan_target`(기본 None)을 `PumpZThermalConfig`에 넘깁니다. `server/__main__.py`의 로더와 같은 기본값입니다.

## 6. 작업 중 발견한 기존 문제 (수정하지 않음)

- **NUC2의 `_shinyeong` 체크아웃**은 `external/` 서브모듈이 모두 `D`(삭제)로 보이는 상태입니다. 디렉토리는 있지만 git 서브모듈로 등록된 것이 아닌 것으로 보입니다.
- **`/v1/health`가 정식 서버에서도 `pump_ok`/`stage_ok`를 `null`로** 돌려줍니다. `diagnose`는 ok를 보고하므로 health 스키마 매핑 문제로 보입니다.
- **`/v1/diagnose` 응답에 `hotplate`/`lamp`/`fan` 블록이 없습니다.** cell의 `diagnose()`는 만들어 주지만 서버 응답 스키마에서 빠지는 것으로 보입니다.
- **`.venv`에 `pexpect`가 없고** NUC1 시스템 python3에만 있습니다. NUC2 접속 헬퍼는 세션 스크래치 디렉토리에만 두었고 레포에는 넣지 않았습니다.
